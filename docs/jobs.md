# Scheduled jobs, health checks and metrics

Data freshness is not a side effect of using the app. A fixed list of jobs keeps every dataset
current, and a small set of endpoints and alerts says whether they are. This page covers the job
manifest, how a job runs, the schedule in development and production, and how to tell that all of
it is working.

## The manifest: `jobs.yaml`

[`jobs.yaml`](../jobs.yaml) at the repository root is the **single source of truth** for scheduled
work. Two things read it:

- `foray scheduler` ([`schedule.py`](../src/foray/schedule.py)), the loop `just scheduler` runs in
  development;
- the production systemd timers, generated by
  [`infra/ansible/tasks/deploy/systemd_jobs.yml`](../infra/ansible/tasks/deploy/systemd_jobs.yml).

Because both read the same file they cannot drift apart. (They used to keep separate lists, and
production silently never scheduled the fire, rain and trail-forage jobs for months.)

Each entry:

| Field | Meaning |
|---|---|
| `name` | The job id. It is the `foray job <name>` argument, the `job_runs` key, the systemd unit suffix (`foray-<name>.service`/`.timer`) and the container name. |
| `command` | The `foray` subcommand and arguments, split on whitespace (so no shell quoting). |
| `interval_hours` | Expected cadence. For `night` jobs it must be `24` (daily) or a multiple of `168` (weekly), because the systemd generator maps it to a calendar day, not a bare interval. |
| `window` | `any`: fires on its own interval at any hour (light, incremental, externally-paced work). `night`: starts only inside **02:00 to 05:00 America/Los_Angeles** (coverage-wide or heavy work). |
| `writer` | `true` if the job writes to Postgres (nearly all do). Writer jobs share a semaphore, see [how a job runs](#how-a-job-runs). |

| `ingest-bulk-osm-trails` | `ingest-bulk osm_trails` | 24 h | night | The OSM trail and forest-road network from Geofabrik extracts (diff load) |

The `ingest-bulk-*` jobs run daily but only do real work when a newer snapshot has been staged,
which happens weekly (below), so they are cheap insurance against missing one.

### The weekly staging workflow

The bulk snapshots are *produced* off the droplet.
[`.github/workflows/bulk-load.yml`](../.github/workflows/bulk-load.yml) runs every Monday at 09:00
UTC (and on demand from the Actions tab, optionally for a single source), pulls the current
application image and runs `foray stage-snapshot --all`. Overlapping runs queue rather than race,
because pruning old snapshots must never delete a concurrent run's objects. Staging needs the
object-storage credentials as environment secrets on the `production` environment. See
[architecture.md](architecture.md#bulk-snapshots).

## How a job runs

Every scheduled command goes through `foray job <name> [--writer] -- <command>`
([`jobs.py`](../src/foray/jobs.py)), which wraps it with:

1. **An overlap guard.** A Postgres advisory lock keyed on the job name. If the previous run is
   still going, the new one records a `skipped` row and exits 0 instead of piling up.
2. **A writer cap.** A `--writer` job waits for one of `FORAY_OBSERVABILITY__WRITER_CAP` (default
   **2**) advisory-lock slots. A pile-up of night-window jobs starting close together therefore
   cannot put more than a couple of concurrent writers on the single-vCPU database.
3. **A subprocess.** The command runs as a fresh `foray` process, so a hung or crashed job cannot
   corrupt the wrapper. The wrapper exits with the command's exit code.
4. **A `job_runs` row** per attempt: `status` (`ok`, `error` or `skipped`), start and end, duration
   and, for commands that report it, the number of rows processed (a command prints
   `FORAY_JOB_ROWS=<n>` as its last line via `jobs.emit_rows`; the wrapper strips that line).
5. **Pings and alerts.** A [healthchecks.io](https://healthchecks.io)-style ping on start, success
   and failure when a URL is configured for that job, and a `foray alert` on failure.

Jobs that share a trigger are separate entries so one failing cannot stop the other from running.

Cache invalidation and the phenology rebuild are part of the jobs, not the wrapper: a job that
changed observations calls `maybe_rebuild_phenology`, which only rebuilds past a threshold, so a
run of small hourly passes does not each trigger the heaviest operation in the system.

## Development and production schedules

### Development: `foray scheduler`

`just scheduler` starts the compose `scheduler` service, which loads `jobs.yaml` and polls every
300 seconds. For each job it skips `night` jobs outside 02:00 to 05:00 Pacific, asks Postgres for
the job's last **successful** run and starts it if `interval_hours` have passed since that run
**ended**. Because the due check reads `job_runs`, restarting the container resumes the real
schedule instead of re-running everything at once. Jobs run one after another in this loop.

### Production: systemd timers

Ansible renders one service and one timer per manifest entry:

- **Service.** A `oneshot` unit that runs
  `docker run --rm --pull always --env-file ... <image> foray job <name> [--writer] -- <command>`.
  `--pull always` means a stale image cannot fail the schema check against a newer database.
  Containers get no persistent volume, so no cache survives between runs.
- **Timer, `night` jobs.** `OnCalendar` at 02:00 Pacific (Sundays only for weekly jobs) with up to
  three hours of randomized delay, and **not** `Persistent`: systemd's catch-up on boot ignores the
  time of day and would run a missed heavy job the moment the box comes back, however far from the
  night window.
- **Timer, `any` jobs.** `OnBootSec=5min`, then `OnUnitActiveSec=<interval>h` with a small random
  delay, and `Persistent=true` so a missed tick runs on the next boot.
- **Housekeeping.** The deploy also removes the units of any job deleted from the manifest (and
  refuses to remove more than three in one deploy, as a guard against a bad expression switching
  off the whole schedule).

The window and jitter settings are `foray_night_window_*` and
`foray_job_randomized_delay_sec` in `infra/ansible/defaults/main.yml`.

To load a freshly staged bulk snapshot before its night window, `just ansible bulk-load <source>` starts that
source's own unit (`foray-ingest-bulk-<source>.service`) now, detached. Let `taxa` finish before starting `inat`.

## Observability

### Health endpoints

None need a cookie. In production `/metrics` is blocked at the proxy (`404` to the public; only the
on-host collector scrapes it), while the three `/healthz*` routes are public so an external uptime
monitor can poll them. Full response shapes are in [api.md](api.md#health-and-metrics).

| Endpoint | Question it answers |
|---|---|
| `GET /healthz` | Can the process answer? No database round trip, so a Postgres blip does not get the container killed. This is what the Docker `HEALTHCHECK` polls. |
| `GET /healthz/data` | Is each layer fresh? `503` if any *blocking* layer's last success is older than its interval times `FORAY_OBSERVABILITY__DATA_FRESHNESS_MULTIPLIER` (default 2). |
| `GET /healthz/backlog` | How much elevation and rain backfill is outstanding, and how fast is it draining? Never fails. |
| `GET /metrics` | Prometheus text exposition of the same data. |

`/healthz/data` takes a layer's last success as the **newer of** its newest `ingest_log` entry and its
job's newest successful `job_runs` row (observations: `ingest_log` only; land and camps:
`layers-land`; dispersed: `dispersed-coverage`; trails: `ingest-bulk-osm-trails`; fire and precip:
`fire` and `refresh-precip`). The job half matters because several ingests are *one-shot per query
version*: once `land:coverage:v2` is logged, the weekly job runs, finds nothing to do and skips, so
the log's timestamp never advances even though the pipeline is healthy. A job that keeps failing, or
never runs, still reads as stale. `fire` and `precip` report staleness but are **non-blocking**, and
`camps` is omitted entirely when `RIDB_API_KEY` is unset, since an unconfigured optional source is
not a freshness problem. When object storage is configured it adds a `bulk-stage:<source>` layer
per registered bulk source, stale when the newest published snapshot is over 14 days old (twice the
weekly cadence) or none ever published.

> **What "fresh" does and does not say.** For a one-shot layer it says the job is running, not that
> the data was re-downloaded. Land ownership, for example, is re-pulled only when its source
> version is bumped (`_LAND_SOURCES_VERSION` in `sources/land.py`); the weekly job otherwise just
> confirms nothing changed.

> **Keep two numbers in step.** The expected cadences `/healthz/data` compares against are
> `Settings.intervals` (`FORAY_INTERVALS__INGEST_HOURS`, `LAYERS_HOURS`, `PRECIP_HOURS`,
> `FIRE_HOURS`), a separate set of defaults from `jobs.yaml`. They currently match
> (24, 168, 24, 24). If you change a cadence in `jobs.yaml`, change the matching interval too, or a
> healthy layer will read as stale (or a stale one as healthy).

### Metrics

`/metrics` is built fresh from Postgres on every scrape (no in-process counters to lose on a
restart):

| Metric | Type | Meaning |
|---|---|---|
| `foray_job_runs_total{job,status}` | counter | `job_runs` rows by outcome |
| `foray_job_http_429_total{job}` | counter | Rate-limit responses recorded for a job (currently always 0: no source wires its retries into the column yet) |
| `foray_job_last_duration_seconds{job}` | gauge | Duration of the most recent successful run |
| `foray_job_last_rows{job}` | gauge | Rows processed by the most recent successful run (only jobs that report it: `ingest`, `revalidate`, `resync`, `genera-refresh` and the elevation, rain and forage jobs) |
| `foray_backlog_depth{kind}` | gauge | Outstanding `backfill_queue` rows (`elevation`, `precip`) |
| `foray_backlog_drain_rate_per_hour{kind}` | gauge | Rows per hour averaged over the last five successful runs |
| `foray_layer_age_seconds{layer}` | gauge | Seconds since a layer's last success |
| `foray_layer_stale{layer}` | gauge | 1 if past interval x multiplier |

In production a Grafana Alloy container on the droplet scrapes `/metrics` plus node and Postgres
exporters and pushes them to Grafana Cloud; the "Foray Planner - Overview" dashboard is committed
as code and re-applied on every deploy. Setup is in [deployment.md](deployment.md#observability-grafana-cloud-issue-338-pr-2).

### Alerts and errors

Everything is opt-in: with nothing configured, a checkout behaves exactly as before.

| Setting | Effect |
|---|---|
| `FORAY_OBSERVABILITY__HEALTHCHECKS_URLS` | JSON map of job name to its healthchecks.io ping URL. A job with no entry is never pinged. `/start` and `/fail` are appended as needed, so a silent job trips the dead-man's switch. |
| `FORAY_OBSERVABILITY__NTFY_URL` | An [ntfy](https://ntfy.sh) topic URL. `foray alert <level> <message>` (and job failures) POST to it. Unset: alerts are only logged. |
| `FORAY_OBSERVABILITY__SENTRY_DSN` | Sentry or GlitchTip DSN; the API and the CLI initialise the SDK when set. |
| `FORAY_OBSERVABILITY__LOG_JSON` | Emit logs as JSON. `FORAY_LOG_LEVEL` sets the level (default `INFO`). |

Alerting never raises: every network call is wrapped, so a failure to alert cannot take down the
job it was reporting on.

## Running things by hand

Run a job exactly as the scheduler would, with its guards and bookkeeping:

```bash
uv run foray job fire -- fire
uv run foray job precip-backfill --writer -- backfill-precip --no-rebuild
```

Or run the bare command (no lock, no `job_runs` row), which is what most `just` recipes do:

```bash
just fire
just resync "--until-done --batch-size 20000"   # a deliberate catch-up, not the hourly default
just bulk-stage inat                             # needs FORAY_SPACES__* configured
just bulk-load inat
```

See [cli.md](cli.md) for every command. Before a heavy one-off write on production (a
from-scratch backfill, say) use the maintenance flag described in
[deployment.md](deployment.md#maintenance-mode).

Look at what has run:

```bash
just psql "SELECT job, status, started_at, duration_ms, rows FROM job_runs ORDER BY started_at DESC LIMIT 20"
curl -s localhost:8000/healthz/data | jq
curl -s localhost:8000/healthz/backlog | jq
```

## Adding a job

1. Add (or reuse) the `foray` subcommand in [`cli.py`](../src/foray/cli.py). Make it idempotent and
   bounded, so it is safe to re-run and to interrupt. Call `jobs.emit_rows(n)` as its last
   action if it has a meaningful row count.
2. Add an entry to [`jobs.yaml`](../jobs.yaml). Decide `window` (heavy or coverage-wide means
   `night`), `interval_hours` (daily or a multiple of 168 for `night`) and `writer`.
3. If it feeds a freshness check, add it to `_layer_specs` in
   [`api/routes/health.py`](../src/foray/api/routes/health.py) and, if its cadence differs, a field
   on `Settings.intervals`.
4. If it should page someone when it goes quiet, add a healthchecks.io check and its URL to
   `FORAY_OBSERVABILITY__HEALTHCHECKS_URLS`.
5. `just test tests/test_schedule.py tests/test_jobs.py`. The next deploy generates and enables the
   timer; nothing else to edit.

Removing a job is the reverse: delete the entry, and the next deploy stops and deletes its units.

## Troubleshooting

| Symptom | Likely cause and fix |
|---|---|
| `/healthz/data` returns `503` | Read which layer is `stale`. Check `job_runs` for its job: repeated `error` rows mean the source failed (the logs say which); no rows at all means the timer is not running (`systemctl list-timers 'foray-*'`). |
| `/healthz/backlog` shows `drain_rate_per_hour: null` | The job's runs recorded no row count, or none succeeded. Every backfill command calls `jobs.emit_rows`; a new one that does not will show `null` however much it does. |
| A `night` job never starts in dev | It only fires 02:00 to 05:00 Pacific. Run it directly with `uv run foray job ...`. |
| Jobs show `skipped` | The previous run of the same job is still going (expected for a long catch-up). If it is hung, find the process holding `pg_locks` for `hashtext('<job>')`. |
| A job is stuck "waiting for a free writer slot" | Two other writer jobs are running (cap 2). It proceeds when one finishes; raise `FORAY_OBSERVABILITY__WRITER_CAP` only after watching database CPU and lock waits. |
| `ingest-bulk-*` fails immediately | Object storage is not configured (`FORAY_SPACES__*`). The command refuses to run rather than silently skipping, so the failure is visible in `job_runs`. |
| Phenology never rebuilds after small jobs | By design: the rebuild is debounced to `PHENOLOGY_REBUILD_THRESHOLD` changed rows. Force one with `uv run foray refresh --with mushrooms` or lower the threshold. |
